# Правила работы с репозиторием

## Структура проекта и организация модулей

Этот RAG-ассистент на Python работает как локальное веб-приложение без входа. `web/index.html` предоставляет чат и загрузку PDF; `api.py` обслуживает `GET /`, `POST /upload` и `POST /ask`. Ответы API содержат `answer` и `sources` с именем PDF и страницей использованного контекста; интерфейс сохраняет эти источники вместе с историей. Старый Telegram-код сохранён, но не является целевым интерфейсом. `app.py` запускает получение обновлений через aiogram (polling); `bot/handlers.py`, `bot/keyboard.py` и `bot/state/` отвечают за взаимодействие с пользователем и состояние диалога. `core.py` отвечает за поиск, переформулирование вопросов, повторное ранжирование через Cohere, проверку контекста через Jev и генерацию через Gemini. `jev.py` содержит клиент TypeSafe REST API с настройками, таймаутом и проверкой ответа; Jev включается явно через `JEV_ENABLED=true` и `TYPESAFE_API_KEY`. `ingest.py` загружает PDF, разбивает текст на фрагменты и сохраняет векторные представления в Chroma вместе с безопасным исходным именем документа. Метаданные `page` остаются с нумерацией от 0; в `sources` страницы начинаются с 1.

В `data/<user_id>/` хранятся загруженные файлы с уникальными именами; в `db/` — постоянные данные Chroma. Каталог `rag/` пуст. В `tests/` находятся pytest-проверки с заглушками; файла со списком зависимостей пока нет. Сохраняй разделение обязанностей между веб-интерфейсом, API, загрузкой документов и поиском.

## Команды сборки, тестирования и разработки

Используй Python 3.12 или новее. Для загрузки PDF через веб требуется `python-multipart` в окружении проекта. Выполняй команды из корня репозитория в PowerShell:

```powershell
& .\venv\Scripts\Activate.ps1
python -m uvicorn api:app --reload
```

Открой `http://127.0.0.1:8000/` в браузере. Для веб-приложения нужен только процесс FastAPI; запуск `app.py` не требуется. Запускай сервер из корня проекта, поскольку пути к хранилищам относительные. Отдельного этапа сборки и команды для воспроизводимой установки зависимостей пока нет.

## Стиль кода и правила именования

Используй отступы в четыре пробела, кодировку UTF-8 и правила PEP 8. Для функций, переменных и модулей используй `snake_case`; для классов — `PascalCase`; для констант — `UPPER_SNAKE_CASE`. Добавляй аннотации типов для новых публичных функций и схем запросов. Сообщения для пользователей на русском языке должны быть понятными. Форматтер и линтер не настроены. В FastAPI выполняй блокирующую обработку документов в синхронных обработчиках (threadpool) или через `asyncio.to_thread` внутри асинхронных обработчиков.

## Правила тестирования

Используется pytest; минимальный порог покрытия не настроен. Для новых тестов используй pytest и файлы `tests/test_<module>.py`; после установки pytest запускай тесты командой `python -m pytest`. Подменяй внешние сервисы заглушками и используй временные базы данных. В первую очередь проверяй изоляцию пользователей, пустые PDF, историю диалога и ошибки API. Вручную проверяй загрузку PDF, соответствие ответов содержимому документов, уточняющие вопросы и изоляцию данных между пользователями.

## Правила коммитов и запросов на слияние (PR)

В истории встречаются как описательные сообщения коммитов, так и сообщения с префиксом `feat:`. Предпочитай короткие сообщения в повелительном наклонении, например `fix: обработай ошибки импорта PDF`. В PR описывай проблему, итоговое поведение, выполненные проверки и изменения конфигурации. Добавляй ссылки на связанные задачи; при видимых изменениях взаимодействия с пользователем прикладывай скриншоты.

## Безопасность и конфигурация

Задавай `GOOGLE_API_KEY` и `COHERE_API_KEY` в локальном файле `.env`; для Jev используй `TYPESAFE_API_KEY` и настройки из `.env.example`. Не выводи ключ TypeSafe, запросы и фрагменты документов в логи ошибок Jev; `BOT_API_KEY` нужен только для старого Telegram-интерфейса. Веб-прототип использует локальный профиль без авторизации; клиентский `user_id` служит фильтром документов и не является контролем доступа. Никогда не добавляй секреты в коммиты и не записывай их в логи. Не добавляй в коммиты загруженные файлы и новые файлы базы данных. Сохраняй существующие локальные данные Chroma, метаданные `user_id` и фильтры поиска.

## Репозиторий и порядок работы

- Основной репозиторий: `https://github.com/TimohaKodit/RAG_system.git`. `origin` должен указывать на него.
- Перед изменениями изучай нужные модули, `git status` и текущую ветку. Сохраняй незакоммиченные изменения пользователя.
- Выполняй поставленную задачу небольшими законченными шагами. Перед изменениями библиотек и внешних API проверяй официальную документацию.
- После каждого законченного шага проверяй изменения и запускай подходящие проверки. Для правок документации достаточно проверить содержимое и `git diff --check`.
- После проверок делай отдельный коммит с понятным сообщением и отправляй его в текущую ветку `origin`. Пользователь поручил коммитить и отправлять изменения в этот репозиторий; повторное подтверждение для обычного коммита и push не требуется.
- Добавляй в коммит только файлы текущей задачи по явным путям. Секреты, `.env`, `venv/`, загруженные документы, локальные данные `db/` и посторонние изменения пользователя должны оставаться вне коммита.
- Перед push учитывай новые коммиты на GitHub. Не используй принудительный push и не переписывай общую историю.
- В конце кратко сообщай, что изменено, как проверено, хеш коммита и результат push. Если коммит или push не удался, прямо сообщай об этом.

## План развития проекта

План составлен по текущему коду. Этапы выполняются по задачам пользователя; запись плана сама по себе не означает запуск всех работ. После завершения этапа отмечай его и обновляй описание проекта при необходимости.

1. [ ] **Воспроизводимый запуск.** Зафиксировать зависимости, добавить `.env.example` без секретов, описать запуск веб-приложения в `README.md`. Вынести параметры подключения и проверку обязательных настроек в конфигурацию. Результат: проект можно запустить по инструкции в новом окружении.
2. [x] **Надёжная загрузка PDF.** Проверять тип и размер файла, использовать отдельные каталоги пользователей и уникальные имена. Обрабатывать пустые PDF и ошибки загрузки и индексации; сообщать об успехе только после добавления текста в Chroma. Сохранять метаданные `user_id` и фильтрацию. Результат: файлы пользователей не перезаписывают друг друга, ошибки понятны.
3. [x] **Надёжный обмен между веб-интерфейсом и API.** Типизировать запросы и историю диалога, обрабатывать таймауты, недоступность API и ошибки ответа, сохранять историю только после успешного ответа. Результат: пользователь получает ответ или понятное сообщение об ошибке, история сохраняется корректно.
4. [x] **Ответы с источниками.** Указывать документ и страницу, на которых основан ответ. Проверять поведение при отсутствии подходящего контекста и при уточняющих вопросах. Убирать дублирующийся код поиска и ранжирования по мере работы с соответствующими модулями. Результат: ответ можно проверить по загруженному PDF. API возвращает источники контекста с именем и страницей, без внутренних путей; это не точные ссылки для каждого предложения. Для старых документов используется имя из существующих метаданных. Пустой контекст и отказ Jev возвращают пустой список источников; уточняющие вопросы и изоляция проверены тестами.
5. [ ] **Проверка основных сценариев.** Покрыть тестами с заглушками внешних сервисов изоляцию двух пользователей, одинаковые имена файлов, пустые PDF, историю и ошибки API. Эти проверки добавлять вместе с изменениями соответствующих этапов; в конце выполнить общий ручной сценарий загрузки PDF и диалога. Результат: основные сценарии проверяются без обращения к платным API и без изменения локальной базы.
